## 2. Key Architectural Decisions

### Next.js 16 specifics
- `middleware.ts` is renamed to `proxy.ts` and exports `proxy` (not `middleware`) — this is a Next.js 16 breaking change
- `params` in page components is a `Promise<{ id: string }>` and must be `await`ed
- Server actions are in `app/actions/` with `"use server"` directive

### Auth pattern
- Two-layer protection: `proxy.ts` redirects unauthenticated requests; `(protected)/layout.tsx` also calls `getUser()` and redirects
- Supabase session is managed via cookies using `@supabase/ssr` (`createBrowserClient` / `createServerClient`)
- Never use `supabase.auth.getSession()` client-side for security decisions — always `getUser()` which validates with Supabase server

### Data write path
All plant creates/edits go through `upsertPlant` server action:
```
Client form → uploadPhoto() → POST /api/upload → Supabase Storage
           → upsertPlant() server action → sanitize → validate → Supabase DB
```
The client never writes to Supabase directly for plant data. Photo upload goes through the API route so server-side type/size validation cannot be bypassed.

### Botanical naming
`genus` (required, capitalised first letter) + `species` (optional, all lowercase) + `cultivar` (optional, no case transform). Displayed as `<em>Genus species</em> 'Cultivar'` via `ScientificName` component. The `search_vector` generated column covers all four name fields (including `common_name`) for future `@@` full-text search queries.

### Photo upload
Client resizes to max 800px JPEG before upload (canvas → Blob). HEIC works on iOS/macOS Safari (canvas converts to JPEG), fails gracefully on Chrome desktop. The server (`/api/upload`) validates type and size on the resized blob. Supabase bucket is configured to 5MB max + MIME type restrictions as a third enforcement layer.

### Validation order in server action
```
upsertPlant(plantId, data):
  1. getUser() — auth check
  2. sanitize (genus, species, cultivar, common_name)
  3. validatePlantInput(clean) — field validation on sanitized data
  4. DB write (insert or update with .eq("user_id", user.id))
```

## 3. Patterns and Conventions to Follow

### File organisation
```
app/
  (protected)/          # All pages requiring auth
  actions/plants.ts     # Server actions for plant mutations
  api/upload/route.ts   # File upload API route
  auth/                 # Public auth pages
lib/
  supabase/             # client.ts, server.ts, middleware.ts
  types.ts              # Shared TypeScript interfaces
  sanitize.ts           # Name field sanitization
  validation.ts         # Server-side validation (FieldErrors type)
  plantName.tsx         # ScientificName component + display helpers
  upload.ts             # Upload constants (types, size limits)
components/             # Shared UI components
supabase/migrations/    # Numbered SQL migrations (001_, 002_, ...)
```

### Error handling in forms
`PlantForm` has two error states:
- `error: string | null` — top-of-form banner for unexpected/auth errors
- `fieldErrors: FieldErrors` — per-field messages rendered under each input

`upsertPlant` returns one of three shapes:
- `{ id: string }` — success
- `{ fieldErrors: FieldErrors }` — validation failure (show per-field)
- `{ error: string }` — unexpected failure (show banner)

### Migrations
Create a new numbered SQL file in `supabase/migrations/` and run manually in the Supabase SQL editor. There is no automated migration runner set up yet — this is a manual step after each deploy.

### TypeScript types
`Plant` interface in `lib/types.ts` is the source of truth. `PlantInsert` is `Omit<Plant, "id" | "user_id" | "created_at" | "updated_at" | "search_vector">`. Generated columns (`search_vector`) and auto-set columns (`user_id`, timestamps) are excluded from insert payloads.

### Supabase clients
- Browser/client components: `createClient()` from `lib/supabase/client.ts`
- Server components, server actions, route handlers: `await createClient()` from `lib/supabase/server.ts`
- Never mix them up — the server client reads cookies for the session; the browser client uses localStorage

### Testing
`npm test` runs Vitest. Tests live next to source files (`lib/sanitize.test.ts`). Only pure utility functions are unit-tested so far; add tests in the same pattern for any new utilities in `lib/`.

### CI
Push to `main` triggers typecheck → lint → build. The build step uses placeholder Supabase env vars — it does not connect to the real database. Keep this in mind: a passing CI build does not mean migrations have been applied.

## 4. Specific Next Steps

### A. Storage bucket — switch to private + signed URLs (REVIEW.md Critical #1)
Currently the `plant-photos` bucket is **public**, meaning any photo URL is world-readable without authentication. This is the highest-priority deferred security item.

**What to do:**
1. In Supabase dashboard: Storage → plant-photos → Configuration → set to Private
2. Create a server utility function:
   ```typescript
   // lib/supabase/signedUrl.ts
   export async function getSignedPhotoUrl(path: string): Promise<string | null> {
     const supabase = await createClient();
     const { data, error } = await supabase.storage
       .from("plant-photos")
       .createSignedUrl(path, 3600); // 1 hour TTL
     return error ? null : data.signedUrl;
   }
   ```
3. Store only the **path** (not the full public URL) in `photo_url` — e.g. `user_id/timestamp.jpg`
4. In server components (plant list, detail page): generate signed URLs before rendering
5. The `PlantForm` preview (client-side `URL.createObjectURL`) is unaffected — that's a local blob URL

   Note: This requires a `photo_url` column migration if you want to strip existing full URLs down to paths, or you can parse the path from the existing URLs (`url.split('/plant-photos/')[1]`).

### B. Logout — revoke session globally (REVIEW.md Critical #4)
In `components/LogoutButton.tsx`, change:
```typescript
await supabase.auth.signOut();
// to:
await supabase.auth.signOut({ scope: 'global' });
```
One line. Invalidates all sessions for the user, not just the current browser.

### C. Reset password — validate token before rendering form (REVIEW.md Should Fix #5)

### E. Orphaned photos on edit (REVIEW.md Nice to Have #13)

### F. Soft delete — decide and implement (open question from spec)
The spec explicitly deferred: "Do we want soft-delete (`status: removed`) visible anywhere in MVP?" The `status` column exists in the schema with CHECK `('active', 'removed')`. Currently the delete button does a hard `DELETE`. Options:
- Keep hard delete (simple, matches current UX)
- Soft delete: change the delete call to `.update({ status: 'removed' })`, add a "Removed" tab/filter in the plant list, or show them greyed out

### G. Multi-select → AI recommendations (roadmap v2)

## 5. Open Questions

**Soft delete visibility** — The most important unresolved design question. Decided to defer but the schema is ready. If you go with soft delete, the `status` filter in the plant list query (`eq("status", "active")`) already excludes removed plants — just add a UI path to see them.

**Storage privacy** — Currently public bucket. The next session should treat this as the first priority if the app moves beyond personal/demo use.

**DB migration runner** — All migrations are applied manually via Supabase SQL editor. If the project grows, consider setting up `supabase` CLI + `supabase db push` workflow, or Supabase's built-in migration management. For now, the numbered files in `supabase/migrations/` document what needs to be run.

**Photo URL format** — Currently storing full public URLs (`https://cycpcsikbmcauokjxarv.supabase.co/storage/v1/object/public/plant-photos/...`). When switching to a private bucket (next step A above), you'll need to decide whether to migrate existing values in `photo_url` to paths, or parse the path from the stored URL. The path extraction approach is simpler: `photo_url.split('/plant-photos/')[1]`.

**Genus capitalization for intergeneric hybrid genera** — `sanitizeGenus` capitalises the first letter and lowercases the rest. This breaks hybrid genus names like `× Solidaster` (where the × prefix should be followed by a capitalised name). Noted in `lib/sanitize.ts`. Rare edge case; handle manually for now, but worth a fix before the app is shared more widely.
